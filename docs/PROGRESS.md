## Decisions & notes (append-only)
- **File 14 billing (Stripe) design + CREDIT_COSTS grounding:** (1) The §10 "BillingService for Stripe" is implemented as a SEPARATE `StripeService` (Stripe API + secret key live here) so it doesn't clobber the existing credit-ledger `BillingService`; money flows one way: verified webhook → `StripeService` → `BillingService.addCredits`. (2) **CREDIT_COSTS finalized** from worst-case external cost, not average, vs a $0.10/credit anchor (cheapest pack ≈ $0.074/credit): search 1 (Places Text Search ~$0.032), **enrichment 2** (Place Details + crawl + LLM, the heaviest), draft 1 (one LLM call), send 1 (no external send cost — margin/anti-abuse). (3) **Idempotency** can't reuse `credit_ledger.ref_id` (uuid) for a Stripe event id (text), so a dedicated `stripe_events` table (PK = event id) is the dedup ledger: claim-then-grant, and roll back the claim if the grant fails so a Stripe retry re-grants (no lost credits). (5) **Webhook-only grant** + raw-body signature verify (reused `rawBody:true` from File 13). (7) **Not-configured is first-class**: no Stripe key → `StripeService` stays dormant, the app builds/runs, the billing UI shows a calm "not switched on" state, checkout returns `{configured:false}`, the webhook 503s — so pasting keys later "just works".

### File 06 decisions & notes
- **`withCreditGate(userId, action, refId, fn)`** (on `BillingService`, `@extrovertai/server`) is **THE MANDATORY PATH** for every paid external action (Files 07/08/09/10). It reserves → runs `fn` → commits on success / refunds on failure. `InsufficientCreditsError` is thrown BEFORE `fn` runs when the user can't afford it. No paid external call may bypass it.
- **Atomicity/race-safety** lives in Postgres functions (migration `20260607020000_credit_functions.sql`): `reserve_credits` takes a per-user `pg_advisory_xact_lock`, checks `sum(delta)`, then debits + writes a `reserved` usage_event — so two concurrent reserves can't both pass on a 1-credit balance (verified). `refund_usage` is idempotent (no double-credit). Balance is **always** `sum(credit_ledger.delta)` — never stored.
- **Security:** these functions are `revoke execute ... from public` + `grant execute ... to service_role`, so only the backend can mint/reserve/refund — never the anon/authenticated API roles. Function signatures were added to the generated `Database` type for typed `.rpc()`.
- **BullMQ on Upstash:** connection built from `REDIS_URL` and passed to BullMQ as **options** (host/port/password/tls parsed from the URL) so BullMQ uses its own bundled ioredis (avoids cross-copy ioredis type/instance conflicts). `maxRetriesPerRequest:null` set. BullMQ 5 supports rate-limiting + delayed jobs (needed for throttled sending in File 10). `metering-test` queue + worker prove the gate end-to-end; real queues are added per-file.
- **Redis verified** (PONG + set/get over rediss:// TLS). The File 01 worker "REDIS_URL absent" warning path is now the real connection.
- Credit costs are still the File-01 placeholders (`search/enrichment/draft/send` = 1 each); finalized in File 14.

### File 08 decisions & notes
- **Credit unit: 1 credit per LEAD enrichment** (`CREDIT_COSTS.enrichment`), NOT per paid sub-call. The whole per-lead pipeline (Place details + crawl + LLM) runs inside ONE `withCreditGate(userId, 'enrichment', leadId, fn)`. Inside `fn`, each external step is individually try/caught so a single failure becomes an honest "not found" (partial result) and still commits — only a truly unexpected error throws → gate refunds (net-zero). Verified live: −1 credit per lead.
- **Bulk = one BullMQ job per lead** (`ENRICHMENT_QUEUE`, payload `{userId, leadId}`) so progress is per-lead and one failure never fails the batch. Worker consumer concurrency = 3 (polite to Places/Firecrawl/OpenRouter). The api is the **producer** (added `bullmq` dep to `apps/api`); the worker is the **consumer**. Shared `buildRedisConnection` util in `@extrovertai/server`.
- **enrichment_status mapping:** existing DB enum is `pending|in_progress|complete|failed` (no `partial` value). Used as coarse progress: `pending`=queued, `in_progress`=running, `complete`=done (full OR partial), `failed`=error. **No "partial" enum value added** (avoided a risky `alter type` migration); partial-ness is surfaced from the DATA instead (email null → UI shows "No email found"). Idempotent: a lead already `complete` is **skipped without re-charge** (verified delta 0).
- **Reviews via Place Details (New)** `GET /v1/places/{id}` with field mask `id,reviews,websiteUri,nationalPhoneNumber,internationalPhoneNumber,rating,userRatingCount` (paid details/reviews SKU; up to 5 reviews). **Cached GLOBALLY by `places:details:{placeId}` (TTL 30d)** in `EnrichmentService` (place data is the same for everyone — global cache cuts cost; the per-lead enrichment credit still applies). Cache write only on `status==='ok'`.
- **One LLM call** does BOTH the review positive/negative split AND the hook (returns `{positive[], negative[], hook}`) — halves model load (free models are rate-limited per File 05). **Deterministic fallbacks** if the LLM is unavailable: `heuristicSplit` (by star rating) + a grounded `fallbackHook` (no-website → "pitch a simple site"; low rating → reputation angle; else neutral). Never fabricates.
- **Email ranking** (`contact-extract.ts`, pure/unit-tested): crawl homepage then up to 2 likely contact pages (`/contact`, `/about`), stop once an email is found (saves crawl calls). Filters image-traps (`.png` etc.), placeholder domains (`example.com`…), hash-like locals. Scores: +site-domain match, +person/role, −generic (`info@`…), −`noreply@`; `noreply` is NEVER `best` (alternates only). **Alternates are NOT persisted** (no `leads` column for them) — only `leads.email` (best) is stored; future migration could add `email_alternates`.

- **Migration `20260608010000_message_drafts.sql`** adds `subject text`, `step_order int default 1`, `approved boolean default false` to `messages` (all `ADD COLUMN IF NOT EXISTS` — idempotent) + index `idx_messages_lead_step`. **No `message_state` enum change** (avoided the enum-in-transaction risk; the `approved` boolean carries the draft-vs-ready distinction). DB types in `@extrovertai/shared` hand-updated to match.
- **Migration application:** no Supabase CLI / `pg` in the toolchain, so it was applied (user-authorized) via a one-off `pg` install (`--no-save`, package manifests restored — pg is NOT a committed dependency) running the committed SQL over `DATABASE_URL`. The CLI's `supabase_migrations` history was NOT updated, but the DDL is idempotent so a later `supabase db push` is safe. **If setting up a fresh DB, the committed migration handles it normally.**

The LLM returns `{messages:[{step,subject,body}...]}`; if step tags are off we fall back to ordering by position; if nothing usable, the job fails → gate refunds.

### File 10 decisions & notes
- **Send credit unit: 1 credit per SEND** (`CREDIT_COSTS.send`), each send wrapped in `withCreditGate('send', messageId)` (so a 3-step sequence = 3 send credits/lead). Keeps the §6 mandatory-gate consistent and makes the out-of-credits PAUSE testable. **Placeholder — File 14 may set send cost to 0** (it's the user's own mailbox). On `InsufficientCreditsError` the campaign is set `status='paused'` (not dropped); failed sends refund (gate net-zero — verified the stopped follow-up cost 0). Verified live: real send −1 credit.
- **Storage:** drafts (File 09 holding area, `campaign_id null`) are LINKED into a campaign on start (`campaign_id` set; still `state='queued'`). `messages` migration `20260608020000` adds `mailbox_id`, `provider_message_id` (Gmail/Graph id — threading + File 11 reply matching), `scheduled_at`, `send_error`. Applied via the same one-off `pg --no-save` path as File 09 (idempotent ADD COLUMNs; `supabase_migrations` history not updated — safe).
- **Gmail send:** `users.messages.send` with base64url MIME (`mime.util`): UTF-8 body via `Content-Transfer-Encoding: base64`, RFC2047-encoded non-ASCII subjects, a self-generated `Message-ID` (Gmail preserves a supplied one). Threading follow-ups = pass the prior step's Gmail `threadId` + `Re:` subject (In-Reply-To header threading deferred to File 11). **Outlook send** implemented (Graph `/me/sendMail`) but UNVERIFIED (no MS creds) — returns no provider id (Graph sendMail is 202/no-body).
- **Typed send failures** (`MailboxSendError.kind`): `reauth` (401/403/invalid_grant → mailbox `status='reauth_required'` + pause campaign + UI reconnect prompt), `rate_limited` (429/503 → retry after 15m), `rejected` (4xx → `state='bounced'`, treated as failure/no charge), `transient` (→ retry after 5m). Token refresh-on-expiry persists the new encrypted access token (`MailboxSenderService`).
- **Throttle/warm-up/rotation (`MailboxCapacityService`):** per-inbox daily cap counted in Redis (`send:count:{mailboxId}:{UTC-date}`, reset daily via TTL). Warm-up ramp for `warmup_state='new'`: `min(daily_cap, 5 + 5·daysSinceConnected)` — day0=5 … reaches cap (default 30) ~day5. **Effective cap surfaced to the UI** (the `/send` plan showed "0/5 today · warming up"). Multiple mailboxes: `pick()` chooses the one with the most remaining headroom (rotation). At-cap → job retried after the daily reset. **Single-mailbox rotation + cap-overflow scheduling are logic-verified** (user has 1 mailbox; the live send incremented the counter; full multi-box + overflow not exercised end-to-end).
- **Sequence engine = chaining (not upfront scheduling):** the campaign enqueues only step-1 per lead; when a step SENDS, `SendingService.nextStep` schedules the next step as a BullMQ **delayed job** (`delay = sequence_steps.wait_days · 1 day`, gaps: step1=0, others=`FOLLOWUP_WAIT_DAYS`=3). Before each step fires, `processSend` re-checks **stop conditions** — `lead.status='replied'` OR a `suppressions` row for the lead email → set the lead's remaining queued steps to `stopped`, no send. **Verified live** (replied lead → follow-up stopped, no send/charge). These signals are populated by File 11; the checks are built + tested now.
- **Worker pacing:** `SendingWorker` concurrency 1 + BullMQ `limiter {max:1, duration:8s}` + a random ≤5s jitter per send → human-like spacing, simple counters (no races). Day-long follow-up delays were NOT waited out; the delayed-job + wait_days math is unit-verified (`waitDaysToMs(3)=259200000`).
- **Campaign status** uses the text column values `active|paused` (+ `done` reserved). `POST /campaigns/:id/status` pauses/resumes; resume re-enqueues the earliest queued step per lead. Mode copied from `users.mode`.

### File 11 decisions & notes
- **Shared compliance guard = `ComplianceService` (`@extrovertai/server`).** THE single place for: suppression check before EVERY send, the tokenized unsubscribe link, and the physical-address footer. **Both File 10 campaign sends (`SendingService`) AND File 11 reply sends (`InboxService`) call it** — no send path duplicates or bypasses it. SendingService's old local `isSuppressed` was deleted and replaced with `compliance.isSuppressed`. `applyCompliance(userId, leadId, email, body)` appends `\n\n--\n<address>\n\nDon't want these emails? Unsubscribe: <url>` and BLOCKS (`no_address`) if `users.physical_address` is empty — campaign start fails fast with `reason:'no_address'` (web prompts to Settings), and `processSend` is the safety net (pauses the campaign). **The sent message body is overwritten with the compliant body** so the inbox/monitor show exactly what went out (and the live test can assert the footer).
- **Unsubscribe** = `GET /unsubscribe/:token` (public, NOT auth-guarded — the recipient isn't logged in). Token is HMAC-signed (same `TOKEN_ENCRYPTION_KEY`-derived secret as mailbox state) carrying `{user, lead, email}`; tamper/garbage rejected (verified). Clicking → `suppress(unsubscribe)` + stop that lead's queued messages + a plain HTML confirmation page. Link base = `PUBLIC_API_URL` or `http://localhost:${API_PORT}` (dev) — **prod must set `PUBLIC_API_URL` to a public tunnel** for the link to resolve.
- **Reply ingestion** = polling (push/webhooks are future). Worker `ReplyPoller` every `REPLY_POLL_SECONDS` (default 120s) reads each connected mailbox. Gmail `listReplies` fetches ONLY the threads we started (`threads.get` for the distinct `thread_id`s of our recent outbound sends — privacy-friendly, not the whole inbox); a message is inbound if its `From` ≠ the mailbox owner. Dedup by `provider_message_id`. On a reply: inbound `messages` row (`direction='inbound'`, `state='replied'`, `step_order=0`) + `reply_events` + lead `status='replied'` (the File-10 stop signal) + immediately stop remaining queued steps. **Stop-on-reply is now fully closed end-to-end** (File 10 had the check; File 11 sets the signal — both verified together live).
- **Reply classification** (`LlmService`): labels `positive|not_interested|out_of_office|auto_reply|unsubscribe|neutral`, conservative (default `neutral`); a deterministic regex shortcut catches explicit opt-outs (`unsubscribe`/`remove me`/…) → routed into suppression even if the LLM is down. Stored in `reply_events.payload.label` (shown as the inbox chip). Live test classified a "Yes, I'm interested" reply as `positive`.
- **Bounces:** detected during the same poll — an inbound from `mailer-daemon`/`postmaster` or a delivery-failure subject → `bounce_events` + auto-suppress the recipient (`reason='bounce'`) + mark the outbound `messages` `bounced`. Heuristic (no provider bounce webhook yet) — documented; verified live with an "Undeliverable" subject.
- **AI reply = approval-by-default, structurally.** `POST /inbox/:leadId/draft-reply` proposes a reply (DraftingService, metered 1 `draft` credit, NOT stored/sent); `POST /inbox/:leadId/send-reply` sends in the SAME thread (compliance-guarded, free — the manual human send is not re-charged). **There is NO auto-send anywhere** — every reply requires the explicit send call, so draft-mode and autonomous-mode both keep the first (and every) reply human-approved. Full hands-off auto-reply would be a future explicit opt-in (NOT built). This satisfies §2's "never auto-fire to a hot lead."
- **Threading:** replies reuse File 10's `MailboxService.send` with the prior message's `thread_id` + a `Re:` subject. Header-level In-Reply-To/References threading is deferred (threadId grouping is enough for Gmail).
- **`messages` now carries inbound rows** (`direction`); the inbox thread = a lead's `sent`/`replied`/`bounced`/`stopped` messages ordered by `sent_at`/`created_at`. **Seed gotcha found (not a product bug):** a Supabase BULK insert with mixed columns turns an omitted `approved` into explicit NULL (violates NOT NULL); the real ingestion uses SINGLE-row inserts where the column default applies — confirmed by the passing live ingestion test.
